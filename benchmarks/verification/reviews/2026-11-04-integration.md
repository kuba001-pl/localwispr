Independent review of the uncommitted context/insertion/cancellation changes, 2026-11-04.

Recommendation: changes are not ready to be described as cancellation-safe or selection-safe. Fix the five issues below and rerun the focused regressions before synthetic desktop acceptance testing. The queued non-GNOME keyboard issue is pre-existing; the other issues affect the new formatter/cancellation/context behavior. No production files, existing benchmark artifacts, desktop settings, clipboard, microphone, or private documents were changed/read by this review.

1. **P1 — a queued non-GNOME paste can execute after cancellation is acknowledged.** Source: `/home/kuba001/.t3/projects/localwispr/src/inject.rs:304-310`, with the cancellation acknowledgement path in `src/daemon.rs:914-917`. The cancellation check runs before `spawn_blocking`; its closure never checks the flag, including after waiting for the keyboard mutex. Aborting and joining the async task does not cancel its queued blocking job. In the disposable fixture, I occupied the only blocking worker, let injection enqueue its keyboard job, set cancellation and awaited task abortion, then released the worker. There were zero keyboard submissions when cancellation returned and one afterward. No chord had started when cancellation was acknowledged. This is not the unavoidable inability to undo keys already sent. Suggested fix: carry cancellation into the keyboard job, check after acquiring the mutex and immediately before starting keys, and use a shared start/cancel gate or equivalent to define the committed point. Regression: `review_queued_keyboard_job_still_pastes_after_cancel`, in `inject-race-harness.rs`; output `review-inject-tests.log`. This fixture replaces desktop side effects and uses a deterministic blocking-worker barrier. `Injector::inject` itself is byte-for-byte identical to current production; `inject-control-flow-verified.txt` records that check. This code path predates the present diff.

2. **P2 — cancelling a GNOME operation after submitting keys can paste the previous clipboard instead of the dictated text.** Source: `gnome-extension/localwispr@localwispr.github.io/extension.js:783-785`, `:972-977`. `_press()` queues key events; it does not acknowledge that the target application has consumed the selection. `CancelInject` immediately restores selections, bypassing the normal consumption grace period. The fixture submits the paste chord, cancels, then models the application's delayed clipboard request: the request sees `original`, not `DICTATED`. That can replace the target selection with unrelated clipboard contents. Suggested fix: distinguish pre-key cancellation from already-submitted paste; keep the injected source available through transfer completion where possible, or at least preserve the normal restoration grace period for committed pastes. Apply the same policy to daemon-owner loss and disable. Regression: `REVIEW: cancelling just after key submission makes a delayed paste consume the old clipboard`, output `review-extension-tests.log`. This reproduces the source-selection ordering with mocked application consumption; it is not an end-to-end real-application test.

3. **P2 — cancelled, never-pasted text remains on the clipboard when restoration is disabled or a backup failed.** Source: extension `:934-942`, `:955-965`, `:997-999`. Only successfully restorable injected sources are added to `_restore`; cancellation/failure cleanup consequently cannot discard the others. One fixture disables restoration, cancels before the 20 ms paste timer, and verifies zero key events but `CANCELLED_SECRET` remains in both CLIPBOARD and PRIMARY. A second fixture keeps restoration enabled, fails the CLIPBOARD backup, and cancels before any keys: the same cancelled text remains in CLIPBOARD. Suggested fix: track every installed source independently of restoration policy and discard owned injected sources on pre-paste cancellation/failure; restore known backups where possible and clear an injected source when no backup exists, preserving newer user ownership. Successful insertion with restoration disabled can retain the requested behavior. Regressions: `REVIEW: cancelling before paste with restoration disabled leaves cancelled text in both selections` and `REVIEW: cancellation after a failed backup leaves cancelled text despite restoration enabled`.

4. **P2 — ordinary ASR terminal punctuation breaks a replacement inside a word.** Source: `/home/kuba001/.t3/projects/localwispr/src/insertion.rs:160-185`, `:233-268`, `:285-306`. `literal_fragment` excludes any utterance ending in `.`, `!` or `?`; for replacements that bypasses the inside-word guard. Replacing `want` in `unwanted` with recognized `need.` produces `un need ed`, while recognized `need` correctly produces `unneeded`. The period is stripped but the decision to add separator spaces has already been made. Suggested fix: recognize a single word plus an inferred ASR sentence terminator as a fragment before prose spacing decisions, retaining word joins without reading the selection. Preserve genuinely literal punctuation according to the formatter's policy. Regression: `review_punctuated_single_token_selection_preserves_word_join`, output `review-format-tests.log`; `format-probe.log` includes additional concrete inputs and outputs.

5. **P2 — the context snapshot is not bound to the eventual paste target/range.** Source: `/home/kuba001/.t3/projects/localwispr/src/daemon.rs:1187-1206`, `/home/kuba001/.t3/projects/localwispr/src/dbus.rs:226-241`, extension `:902-904`, `:924-927`, `:968-972`. The context response contains text and a replacement boolean but no focus/range generation. Its focus watchers are disconnected when the response is returned. Injection then takes a new focus baseline, silently accepting a different editor if focus moved in between. During clipboard preparation, its watchers check window/Shell focus and content properties, but no surrounding-text or caret/selection changes. Two fixtures reproduce this: switch windows after context returns but before InjectCancellable, or change the selected range during preparation in the same field. Both still emit all four Ctrl+V key events. Suggested fix: pass a request-scoped context/focus generation into injection, retain invalidation across context-to-injection handoff, and invalidate/revalidate the committed surrounding range after clipboard preparation and before key submission. Conservative abort or unformatted fallback is preferable to applying stale adaptation. Regressions: `REVIEW: focus changed between context response and injection is adopted as the new paste target` and `REVIEW: selection/caret changes during clipboard staging are accepted by the current request`. These are avoidable gaps before the final commit, distinct from the remaining OS atomicity limit.
